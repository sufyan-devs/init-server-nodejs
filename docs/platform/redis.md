# Redis

> **Verified against the code on 2026-10-19.** Runtime check on 2026-09-02 against Redis 8.2.7
> (Memurai): the app connected to db 11; session, per-user index, OTP and rate-limit keys were
> present there and absent from db 0, with no raw IP or email in any key name. **Not exercised:** a
> real Redis Cluster, failover, or Redis going down mid-request.

Redis holds everything **ephemeral, high-churn and rebuildable**. The database holds everything
durable. Getting this line wrong in either direction is expensive, so it is worth stating plainly:

| | Redis | Database |
|---|---|---|
| Holds | sessions, lockout counters, rate limits, OTP codes, password-reset sessions | users, roles, audit log |
| If wiped | everyone logs in again; pending OTPs and lockouts are gone | nothing — it is backed up |
| Written | constantly | rarely |

Losing a session is a re-login. Losing a user is a company-ending incident. That is the whole rule.

---

## Which database

**This app uses Redis logical database `11`, not `0`** — `REDIS_DB`, defaulting to 11 in
`src/config/env.ts:237-239`. A developer machine usually runs several projects against one Redis,
and `npm run db:reset` calls `FLUSHDB` (`src/scripts/reset-db.ts:32`): on the default db 0 that
wipes whatever else is running.

The index is written into the connection URL (`src/utils/redisClient.ts:7-25`, `30-33`), not passed
as the `database` option. node-redis parses `url` **after** the plain options, so a `database`
option is silently overridden by the URL's index — which is 0 when the URL omits one. Setting
`REDIS_DB=11` alongside `REDIS_URL=redis://host:6379` would then look correct and still write to
db 0. Building the index into the URL is what makes `REDIS_DB` authoritative.

If `REDIS_URL` carries a db index that disagrees with `REDIS_DB`, the process **refuses to start**
(`redisClient.ts:16-21`). Silently preferring one would let a service read an empty keyspace,
which looks identical to having lost every session.

Logs name only the host and db index, never the URL, because the URL may carry a password
(`redisClient.ts:35-37`). In production, a non-localhost Redis is connected over TLS
(`redisClient.ts:61-63`).

## Key map

Every key is built by a helper in `src/utils/redisKeys.ts:25-39`, **never inline at a call site** —
a typo silently creates a second namespace that nothing reads.

| Key | Holds | TTL (default) |
|---|---|---|
| `sess:<sid>` | the session record, JSON | `SESSION_EXPIRY_MS`, 7 days (`env.ts:5`), sliding but never past the 30-day absolute cap |
| `user:<id>:sessions` | SET of that user's sids — the index | raised to at least the session TTL whenever a session is saved or refreshed (`Session/repo.ts:55-61`) |
| `rl:<bucket>:<scope>:<hash>` | rate-limit counter; scope is `ip` or `acct` | the bucket's window |
| `otp:<purpose>:<hash>:code` / `:attempts` | the code and its wrong-guess count | `OTP_EXPIRY_MINUTES`, 10 (`env.ts:218`; set at `modules/auth/helpers/otp.ts:79-82`) |
| `otp:<purpose>:<hash>:send_count` | codes sent in the window | `OTP_SEND_WINDOW_MINUTES`, 60 (`env.ts:221`; `otp.ts:83`) |
| `login:fail:<userId>` | failed-login counter | `LOCKOUT_WINDOW_SECONDS`, 900 (`lockout.service.ts:29-32`) |
| `login:lock:<userId>` | lockout marker | `LOCKOUT_DURATION_SECONDS`, 900 (`lockout.service.ts:35`) |
| `reset_session:<resetId>` | the email of a verified password reset | `RESET_TOKEN_EXPIRY_MINUTES`, 5 (`env.ts:229`, same in `.env.example`; set at `modules/auth/services/session.service.ts:285-289`) |

`<purpose>` is `verify_email` or `password_reset` (`otp.ts:30-33`). `<sid>`, `<id>`, `<userId>` and
`<resetId>` are generated by the server.

**Every client-supplied segment is SHA-256'd to 32 hex chars** (`identifierHash`,
`redisKeys.ts:18-23`): the email in OTP keys and the IP or email in rate-limit keys. Two reasons:
`:` is the delimiter and an IPv6 address is full of them — `::1` pasted raw turns one segment into
several, so a key can no longer be parsed back into its parts; and keys reach SLOWLOG, MONITOR and
metrics far more readily than values do, where an email or IP is personal data.

The cost is that you cannot find an OTP by eyeballing the address. To look one up by hand:

```bash
node -e "console.log(require('crypto').createHash('sha256').update('User@Example.com'.trim().toLowerCase()).digest('hex').slice(0,32))"
redis-cli -n 11 GET "otp:password_reset:<that hash>:code"
```

**Every key carries a TTL** — each write above passes one. A key without an expiry is a memory leak,
and for a counter it is a permanent lockout.

## The session record

The cookie carries `<sid>.<secret>` (`session.service.ts:148`). Redis stores **only
`SHA-256(secret)`** (`session.service.ts:131`), so a Redis dump cannot be replayed as a live
session — the same reasoning that applies to password hashes.

### What authenticating a request costs

`verifySessionToken` (`session.service.ts:154-180`) reads the record and its TTL in **one round
trip**: `GET` and `TTL` on the session key in one `MULTI` (`Session/repo.ts:96-101`,
`redisKeys.ts:71-76`). It then compares hashes with `timingSafeEqual`, checks the 30-day absolute
deadline, and checks that the session belongs to the portal of the route. **No database call.**

It writes only when less than half the session TTL remains (`Session/repo.ts:19`, `125-137`): an
`EXPIRE` on the session key, then a `TTL` check and, if needed, an `EXPIRE` on the user's index. That
refresh is fire-and-forget — the request does not wait for it (`session.service.ts:71-81`). A
session found past its absolute deadline is deleted the same way (`session.service.ts:88-92`).

The refresh is a pure `EXPIRE`, never a rewrite of the record (`Session/repo.ts:133-135`).
**Real world:** Ali switches his active role on his phone while his laptop's request is mid-flight.
If the laptop's request re-saved the record it read at the start, it would put the old role back.
For the same reason `lastSeenAt` is set only at login and at role switch
(`session.service.ts:141`, `239`), not per request.

There is no epoch counter. It exists to invalidate tokens you cannot enumerate, and we can:
`user:<id>:sessions` indexes every live session, so logout-all deletes them directly. Keeping it
would have cost a second read on every request for nothing.

### What is in it

The record (`modules/auth/models/Session/types.ts:32-45`) is kept deliberately small: sid, secret
hash, user id, active role, available roles, portal, device metadata, timestamps, and the five
display fields `req.user` promises (`email`, `firstName`, `lastName`, `emailVerified`,
`profileImage`, in `session.user`). Those five are what removed the last database read from the auth
hot path.

**Never store the whole user document in it.** The five are a closed list chosen because they are
display-only and change rarely; each one added is another field that can go stale and another write
path that has to call `syncSessionUser`. Anything that decides *access* — roles, status,
permissions — either lives here already (`availableRoles`) or must invalidate the session rather
than be cached (`revokeUserSessions`). Both are in `modules/auth/index.ts:27-31`.

`availableRoles` is copied in at login and rewritten by `syncSessionRoles`
(`modules/auth/index.ts:33-34`) when an admin approves a role request or activates or deactivates a
role, and by `sessionService.syncRoles` directly when `request-role` is auto-approved
(`modules/auth/services/auth.service.ts:261`). A session whose `activeRole` the user no longer holds is deleted instead
(`session.service.ts:269-283`). Like `syncUser`, the sync reads every sid in the user's index. A
role change made by hand in the database is not synced — see
[../decisions.md](../decisions.md) (closed question 6).

## Scaling rules

These are [performance-practices](../standards/performance-practices.md) applied to Redis. The
rules are about round trips and unbounded work, so they transfer directly.

**Bounded by the per-user cap.** After every login the user's index is pruned to
`SESSION_MAX_PER_USER` (10 by default, `env.ts:192`), evicting the oldest sessions
(`session.service.ts:94-104`, `145`; `Session/repo.ts:139-165`). Listing devices and logout-all read
that index, so they touch about that many keys. Listing reads every sid in the index, then returns
at most `SESSION_MAX_PER_USER` (`session.service.ts:207-220`). The prune is fire-and-forget, so for a
moment after a login the index can hold one more than the cap. Without the cap, a scripted login
loop grows the set forever: memory that never returns, and a list call that gets slower with every
login.

**Per-key commands, issued concurrently — deliberately not one multi-key command.** A single
`MGET`/`DEL` across many keys is one round trip on a single Redis and a **CROSSSLOT error on a
cluster**, because multi-key commands require every key in one hash slot. `findManyBySids`,
`deleteAllForUser` and `pruneToLimit` therefore issue one command per key through `Promise.all`
(`Session/repo.ts:63-66`, `119-123`, `158`). node-redis flushes commands issued in the same tick as
one socket write, so this costs about one round trip. The rate limiter does the same, one `MULTI`
per counter, and `clearFailures` deletes `login:fail:<id>` and `login:lock:<id>` as two separate
`DEL`s (`modules/auth/services/lockout.service.ts:52-54`), because those two keys can land in
different slots.

**Never `KEYS` or a wildcard scan.** The per-user SET is the index — that is why it exists.

## Failure modes

| Redis is | Effect | Why |
|---|---|---|
| **down at boot** | process exits (`src/server.ts:121-125`) | a server that rejects every login while reporting healthy is worse than one that does not start |
| **down at runtime** | authenticated requests get a **5xx**, not a 401 (`modules/auth/middlewares/authenticate.ts:30-31`, `51-52`) — so clients do not drop sessions that are still valid. Logins fail. **Rate limiting passes traffic through** (`src/middlewares/rateLimit.ts:100-108`). OTP sends are refused (`otp.ts:64-73`) | the limiter fails *open* deliberately — failing closed turns a cache outage into a total outage |
| **flushed** | everyone logs in again; pending OTPs, reset sessions and lockouts are gone | sessions are rebuildable by design |

The asymmetry is intentional: auth failing closed is correct, limiting failing open is correct.
One protects data, the other protects availability.

A failed-login count that cannot be written is logged and skipped, not raised
(`lockout.service.ts:44-49`), so a Redis error during a wrong-password attempt does not turn into a
5xx.

## Version requirement

**Redis >= 7.0.** The limiter uses `EXPIRE key ttl NX` (`redisKeys.ts:136-138`), which is 7.0+. An
unconditional `EXPIRE` would push the reset forward on every hit, letting a client hammering a
blocked endpoint renew its own block indefinitely.
